\section*{2. Task 1 --- Object storage and parallel teacher labelling (method)}
\textbf{Design.} SeaweedFS (S3 gateway) in namespace \tc{data}, buckets \tc{datasets} and \tc{models}. An Indexed Job (\tc{completions=parallelism=2}) in \tc{pipeline}; worker $i$ labels records with $n \bmod 2 = i$. Shards are complete (every $n$ has one residue), disjoint, and balanced ($1500+1500$).
\textbf{Cleaning} keeps a reply only if: valid JSON; exactly keys \tc{intent,date,time,place}; intent in the eight allowed; each non-null slot occurs in the command; not a duplicate. Check: $N_{in}=N_{kept}+\sum N_{rejected}$; publish SHA-256 of \tc{train.jsonl}.
\textbf{Measure:} per-shard counts \ph; Job duration \ph; rejection counts per rule \ph; kept \ph; checksum \ph. \textbf{Limitation:} both workers share one host CPU for Ollama, so speed-up may be small.

\section*{3. Task 2 --- Student training (method)}
Sequence-level KD (Kim and Rush, 2016): train on the teacher's best sequence $y^*$ with cross-entropy,
\[\mathcal{L}(\theta)=-\sum_{t=1}^{T}\log p_\theta\!\left(y^*_t\mid x,y^*_{<t}\right),\]
prompt tokens masked. Input format \tc{Command: <text>\textbackslash nJSON: <json>} --- identical to the service prompt. Pythia-70M, first 1,500 cleaned records, AdamW $\approx5\times10^{-5}$, batch 8 (188 steps/epoch), 3--4 epochs, seed fixed, all values in \tc{training/config.yaml}; \tc{make train}, \tc{make train SUBSET=50}. v1 and v2 differ by a recorded setting; both get SHA-256 and a GitHub Release asset; weights are never committed.

\section*{5. Task 4 --- Kubernetes}
Namespace \tc{app}: Deployment (2 replicas; requests 250m/512Mi; limits 1 CPU/1Gi; liveness \tc{/healthz}; readiness \tc{/readyz}; RollingUpdate maxUnavailable 0, maxSurge 1) $\to$ Service :80 $\to$ Ingress (Traefik); HPA min 1, max 2, CPU 70\%. HPA rule:
\[\text{desired}=\left\lceil \text{current}\times\frac{\text{utilisation}}{\text{target}}\right\rceil,\quad\text{e.g. }\lceil 2\cdot 140/70\rceil=4\to\text{clipped to }2.\]
Procedures: replica distribution via \tc{X-Served-By}; rollout by \tc{kubectl set env} (v1$\to$v2) under load then \tc{rollout undo}; pod deletion under load; three cold starts. Only the YAML fields were tested. Results: failed requests during rollout (target $\le0.5\%$) \ph; version after rollback \ph; recovery time \ph; cold starts \ph; HPA events \ph. \textbf{Limitation:} single host, no node-failure tolerance.

Example: $\log_2 1002=9.97\Rightarrow p=22$, 1022 usable. \textbf{NACL algorithm:} sort rules ascending; first rule matching CIDR (source inbound, destination outbound) and protocol/port decides; none $\Rightarrow$ deny. Inbound: 100 deny 198.51.100.0/24 (all); 110 tcp 80; 120 tcp 443; 130 tcp 22 from 10.20.5.128/27; 140 tcp 1024--65535 from 10.20.0.0/22. Outbound: 100 tcp 8000 to 10.20.0.0/22; 110 tcp 1024--65535 to 0.0.0.0/0.
\textbf{Why replies need rules:} a NACL is stateless; a reply is a new packet judged alone. \textbf{Why order matters:} rule 100 precedes 110/120, otherwise 198.51.100.0/24 would be allowed on 80/443. \textbf{Side effect:} rule 110 also permits outbound TCP 8000 to anywhere. \textbf{Tested:} own evaluator 11/11 packets; the instructor's six-packet \tc{nacl\_sim.py} was not run.

\section*{8. Task 7 --- Performance and cost (method)}

\[\text{cost per 1000 req}=\frac{C_h}{3600\cdot\text{throughput}}\times1000,\]
assuming billing at limits (an assumption). Error budget $=(1-\text{SLO})\times N$.
